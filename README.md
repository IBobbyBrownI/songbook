# Songbook

1. Как запустить с нуля
    * Клонировать репозиторий: "git clone https://github.com/IBobbyBrownI/songbook.git";
    * Создать файл .env в корне, копировать содержимое .env.example, указать сови DB_USER и DB_PASSWORD;
    * Запустить контейнеры: "docker compose up -d --build";
    * Подождать пока MySQL полностью запустится (секунд 20 на всякий случай)
    * Применить миграции: "for f in migrations/*.sql; do docker exec -i songbook-databse-1 mysql -u root -psecret songbook < "$f"; done";
    * Подключить seed для заполнения БД данными: "docker exec -it songbook-php-1 php seed/seed.php"
    * Открыть в браузере: localhost:8000.


2. Архитектурные решения
    * PHP: Для разработки, я выбрал PHP с Symfony-компонентами. Для полного понимания картины. С фреймворком было бы возможно быстрее, но к чему эта быстрота если запомнится лишь "Куда нажимать чтобы получилось что-нибудь". Для перспективы лучше использовать отдельные компоненты и понять как они работают. Мне понравилось какой пример привел AI. На моем этапе, работа с фреймворком будет похожа на микроволновку, положил еду, она разогрела вопросов нет, но готовить не научила. Какие есть приемущества при работе с компонентами: Во-первых это сокращает количество кода как например при использовании голого php; Во-вторых куча моментов, которые компоненты делают автоматически.

    * DB: Для работы с БД, я выбрал MySQL. Для работы нашего приложения, необходима БД с возможностью создавать отношения М:М (Многие ко многим), MySQL проще для начального изучения, по-сравнению с PostgreSQL, хоть он и мощнее и возможно лучше, но в то же время она намного более функциональна чем SQLite, тем более для выхода в продакшен, испольщуя SQLite все-равно придется переезжать на MySQL либо другую Бдшку, поскольку SQLite блокирует всю базу целиком при записи. Если два пользователя одновременно добавляют песню, одному придется ждать другого, тут без шансов!

    * Окружение: Тут без сомнений я выбрал Docker. Почему Docker а не Vangrant? Зачем для развёртования и запуска программы использовать ядро гостевой ОС, если можно использовать ядро своей ОС, и изолировать все процессы приложения. Это намного быстрее и занимает меньше мб, разница в минутах и гигабайтах, да и потом, тратятся ресурсы на поддержание ядра гостевого ОС. В Docker можно описать все что нужно приложеню в одном файле (Dockerfile либо Docker-compose), что позволяет спустя долгое время просто запустить проект и получить полностью идентичное окружение, какое было при разработке этого приложения. Почему не локальная установка? Самому всё поднимать, подключzть и т.д.? А если нужно будет открыть проект на другом компьютере? Придется устанавливаться все необходимые для запуска компоненты. Поэтому этот вариант даже не рассматривается.

    * Фронт: При работе с фронтом, выбор упал на Twig. Одно из требований, было исключить XSS (Межсайтовый скриптинг), Twig делает это автоматически. Касательно архитектуры приложения, Twig помогает избавиться от бесконечных include + Если где-то будет обнаружена ошибка, то Twig сразу скажет об этом, а не "сломанно" выдаст html.

    * Транслит для Slug: В качетсве транслита для slug, мой выбор упал на cocur/slugify. Поскольку он просто берет строку и возвращает готовый slug с правилами аж для десятков языков. Не нужно писать кучу реплейсов, все уже готово. Казалось бы, есть еще вариант behat/transliterator, вроде тоже не плох, но такие вещи как пробелы, приведение к нижнему регистру, все пришлось бы делать самому, и вообще он создавался для других целей (чтобы превращать русские слова в английские для имен php-методов, а не для URL). Создавать всё в таблице выбор мазохиста xD.

    * Проектирование схемы для БД: В качестве инструмента я выбрал dbdiagram.io, приятный интерфейс, наглядно видны зависимости, практика в написании бд при помощи кода, в будущем может быть полезно.

    * Как рендерится chordPro: Подход, который я использовал - Grid-flexbox. Почему? потому что flexbox выстраивает блоки в ряд, в то время как grid заранее нужно знать сколько будет блоков чтобы расчертить аккорды (3 колонки - 3 аккорда), пришлось бы либо делать inline-стили в php, либо делать фиксированное кол-во колонок с запасом. В свое время если flexbox не вмещает все в один ряд, он просто переносит в другой. Почему не <ruby>? изначально предназначен для иероглифов и может нестабильно отображаться на разных шрифтах а абсолютное позиционирование проит моноширный шрифт для всего текста, что ограничивает дизайн. По сути, flexbox решает ту же задачу что и grid, но с flexbox(ом) проще, поэтому выбор упал не него.
        - Длинные строки переносятся с помощью "flex-wrap: wrap", вместо горизонтальной прокрутки, блоки аккорды+слог не разрываются, это намного удобнее на мобильных версиях.
        - XSS защита проверяется через htmlspecialchars, что исключает инъекции (Так, JS-команду просто превратит в строку).

    * SHA-256 - в нашем проекте, это заглушка для будущего, сейчас у нас не используется, но в дальнейшем при импорте из других источников, или пользовательском добавлении, fingerprint будет определять, есть эта песня или нет.

    * ChordPro AST - (Abstract Syntax Tree) По своей сути, играет роль связующего звена, между парсером и рендером. Хранит информацию в виде:      
        {title: Великий Бог} metadata: { title: "Великий Бог", key: "C" }
        {key: C}
        sections: [
        {c: Куплет 1} { type: "comment", text: "Куплет 1" }
        [C]Господь Вели[F]кий { type: "line", parts: [
        { chord: "C", text: "Господь Вели" },
        { chord: "F", text: "кий" }
        ]}
        ]

    * Выбор артиста с ролью: реальзован как список всех артистов с checkbox и выпадающим списком ролей. Простое решение исключительно для MVP.

    * Удаление через POST: Кнопка "Удалить" реализована с методом POST. GET запросы не должны менять состояние сервера, в противном случае поисковые роботы, браузерный prefetch (Функция которая заранее прогружает ссылки чтобы они быстрее открывались когда пользователь тыкнет по ним) или случайный клик удаляли песню. Звучит весело, представляю экспириенс пользователя который постоянно случайно удаляет песню после практически каждого шага xD.
        - Помимо этого, я добавил еще 'onSubmit' на кнопку, чтобы случайно не удалить песню при нажатии
    
    * Транзакции при сохранении и редактировании песни. Операции UPDATE песни и INSERT в song_artists (список артистов песни) атомарны (выполняются по-отдельноси), для предотвращения поврежденных данных в БД при сбоях, данные добавляются только после того, как все операции прошли успешно.

    * Slug и разрешение конфликтов при создании песни с одинаковым названием: Решил путем добавления суфикса -2, -3 и т.д. в slug песни, таким образом при создании песни с одинаковым названием будут генерироваться разные slug. Функция делает запрос в БД, если песня с таким же slug уже существует, значит обрабатываем через счетчик и добавляем суфикс в конце, получается "my-god-2". Если песня с таким slug тоже существует тогда опять обрабатывается счетчик и уже будет "my-god-3", если такого slug в базе нет, сохраняется песня.
        - Slug не меняется, даже если изменили название песни. Это сделано для того, чтобы ссылка не ломалась, если пользователь успел поделиться ей или сохранил у себя в закладках. Это можно поправить, чтобы например старая ссылка вела к новой (сделать ридерект на новую ссылку), но для MVP проекта оставим так как есть.

    * Удаление артиста: При удалении артиста проверяется, есть ли у него песни в таблице song_artists. Если есть - удаление запрещено с соответствующим сообщением мол: "Ему нельзя, у него еще X песен, сначала пусть с ними разберется и если всё ок, то я не против". Это гарантирует что песня не останется без единого артиста.
        - Если у артиста нет песен, то он удаляется и редирект на список артистов.

    * Поиск и фильтры:
        - Поиск и фильтры реальизованы через GET-запросы на главной странице
            1) '?q=' - поиск по названию песни или артисту, регистронезависимый благодаря LIKE.
            2) '?key=' - фильтр по тональности
            3) '?license' - фильтр по лицензии
        Все три пораметра работают совместно и по итогу получаем подобный URL: `?q=lord&key=C&license=public_domain`.

        - Динамический SQL: Все Where условия добавляются в массив $where, для дальнейшей конкатенации с sql-запросом. Поскольку элементов может быть несколько, их нужно как-то разделить, для этого я использваол функцию implode(), которая принимает в качестве параметров принимает разделитель (AND в нашем случае) и массив по которому нужно пройтись $where, далее передается в prepare и экранируется, что исключает инъекции.

        - Whitelist: значения license и key проверяются по белому списку из разрешенных значений. Значения которых нету в whitelist игнорируются. Так например нельзя в поле URL ввести инъекцию и обновить страницу.

        - Для чего GET, почему не POST: GET позваоляет записывать данные в URL и копировать ссылку с заложенными данными.

4. Что узнал нового
    * Начну наверное с подключения Docker, пусть и на момент записи я еще не уверенно разбираюсь что происходит, но у меня получилось сделать билд!!!
    Docker позволяет хранить в себе рабочую версию проекта, со всем окружением внутри! В чем отличие от виртуальных машин? ВМ думает что она отдельный компьютер + на нее отводится свое ядро и затрачивается кууууча ресурсов, по сравнению с докером. Всё что нужно собрать образ и запустить контейнер.

    На момент написания я еще разбираюсь с тем что конкретно и как произошло с моим проектом, но в целом картина такая, в дальнейшем я изменю этот пункт.

    * Composer: Отличная штука которая упрощает написание кода, ее цель: автоматически подключать все классы и компоненты, вместо тысячи require, просто подключаем один раз autoload.php и все классы из vendor/ загружаются автоматом. Уменьшает шансы что-то забыть.

    * Компонент Symfony/Dotenv: Классная штука, отвечает за безопасность (файлы .env не коммитятся, иначе ваши пороли будут в сети) и уменьшении кол-ства кода и гибкость (если что-то нужно будет поменять, просто меняем в файле .env). Как работает? У нас есть файл .env, в котором отражены ключи для работы с БД: HOST, NAME, PORT, USER, PASSWORD. объект класса Dotenv, берет данные из .env и хранит их в виде ключ=значение. Что нам дает? При помощи Dotenv мы можем обращаться к глобальной переменной $_ENV и брать оттуда данные $_ENV["DB_NAME"].

    * PDO (PHP Data Object): Форма работы с БД, позволяет отправлять и обрабатывать запросы, например $pdo->query(), позволяет сделать запрос без входных данных, что исключает появление инъекций (SELECT NOW()), если же входные данные необходимы, в таком случае придется использовать prepare и execute.

        - PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION - при обнаружении ошибки, pdo сразу выдаст ошибку, завершая процесс. Без нее, pdo тихо выдаст false и разбирайся что где случилось, ERRMODE_EXCEPTION как резаный будет кричать "Ошибка!!!".

        - PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC - И так, фетч мод, говорит всему нашему проекту, что данные приходящие из бд будут хранится в виде ассоциативного массива. Представим что у нас есть таблица, колонки id, title, элемент 1 -> "Ангелы у трона Твоего", Ассоцитивный фетч даст "id"= 1; "title"="Ангелы у трона Твоего"; Num-фетч, даст 0=1 (где 0 это колонка id) и 1="Ангелы у трона Твоего" (где 1 это колонка title), не удобно; Both-фетч вообще дает и то и другое вместе. По-умолчанию FETCH_MODE использует FETCH_BOTH.

        - Всё это можно подключать поодельности, но куда проще указать в корне.
    
    * БД
        - Индекс - позволяет намного быстрее искать нужные записи в БД, т.к. использует остортированные данные. Без индексов чтобы найти 200 записей из 10000 нужно будет прочитать все 10000 "Этот подходит, запишу/этот не подходит, не запишу", а так список отсортирован и получается в 50 раз быстрее (в данном случае). Пример из таблицы songs: Нужно найти все песни в тональности "Am" (SELECT * FROM songs WHERE original_key = "Am"), вместо того чтобы проверять каждою запись он возьмет из отсортированного списка нужную "кучку".

        - UNIQUE (на примере slug из таблицы songs) - Без Unique база пропустила бы 2 песни с одинковым названием и slug, ведь PK на id гарантирует что сами id будут разными, а при добавлении они и будут разными, пусть и с одинаковым содержимым что в следствии при при попытке запросить slug который имеют 2 записи, ответ будет именно 2 записи. UNIQUE в свою очередь не даст добавить песню если найдет такой же slug в БД, что позволяет исключить такой конфлик. Почему UNIQUE а не PK? можно было бы сделать как в song_artists, несколько PK, НО:
            1) id - компактнее до 4 байт, а slug мы указали 255, скажется на скорости прочтения в будущем;
            2) id - никогда не меняется, а slug может, он ведь берется из названя песни, а песню можео будет переименовать;

        - SHA_256 - Математическая функция, которая берет текст и превращает его в уникальную строку состоящую из 64 символов (букв и цифр). В нашем проекте используется для исключение дубликатов, но вообще используется для хранения поролей, точнее не совсем поролей а результатом вычисления из пороля, при утечке данных, пароли все-равно останутся неизвестными, в Git каждый коммит идентифицируется хэшем и т.д. Иными словами - шифратор.

        - composite primary key - составной первичный ключ. В нашем проекте, расположен в таблице song_artists, для чего используется? При создании песни, у нее может быть несколько авторов, но играющих разную роль, так например песню Reckless love перевел: совет переводов ц. Благодать (например), а аранжировку сделал: Владислав Кривобродский.

        - Миграции и seed - Миграции это файлы с sql-кодом, с помощью которых можно поднять всю бд с правильной структорой, при помощи одной команды, в дальнейшем она заполняется при помощь алгоритма, который прописан в seed.php и описывает чем БД будет заполняться, как будет шифроваться хэш и т.д. Можно провести аналогию, при помощи миграций, мы вспахиваем поле, когда поле готово, мы можем засыпать его семенами seed(ами). Используется повсеместно при тестировании и демонстрации заказчика работоспособности приложения с тестовыми данными.

        - ON DELETE RESTRICT - запрещает удалять запись, пока на нее ссылается связь с другой таблицы, используется когда удаленние записи опасно. Например, мы не хотим удаить пользователя у которого есть заказы, мы же не хотим случайно потерять заказы.

        - ON DELETE CASCADE - наоборот база автоматически удаляет все строки в song_artists при удалении песни, зачем их хранить если самой песни то нет :D

        - INNER JOIN - Способ склеить 2 таблицы "Покажи только песни, у которых есть артисты", песни без артистов, иичезают

        - LEFT JOIN - "Покажи все песни, даже если нет артиста", в таком случае поле для артиста будет просто null.

        - UPDATE - Позволяет обновить данные в записи. У нас используется для редактирования песни.

        - Динамический sql: 
            1) Паттерн: Собираем условия в массив, параметры в массив, склеиваем с помощью implode() и передаем в prepare.

        - GROUP_CONCAT - склеивание нескольких строк в одну с разделителем.

        - SEPARATOR - разделитель для GROUP_CONCAT

        - impode() - функция склеивания массива в строку с разделителем (в нашем проекте с AND)

    * cocur/slugify - позволяет генерировать slug(и), которые используются в URL для безопасного использования и понятной читаемостью url.

    * Regex - это язык шаблонов для поиска в тексте, у нас в проекте использовался для поиска директив и их значений, а также для поиска аккордов в тексте. Пример в коде "/^\{(\w+):\s*(.+)\}$/u" где:
        - ^ - с начала строки;
        - \{ - открывающая фигурная скобка;
        - (\w+) - слово (title/key/c) в первый "карман";
        - : - двоеточие;
        - \s* - пробелы (может и не быть);
        - (.+) - значение директивы во втрой "карман";
        - \} - закрывающая фигурная скобка;
        - $ - конец строки.

    * preg_match и preg_split
        - preg_match: функция, задача которой проверить, подходит ли вся строка целиком под шаблон, и если да — вытащить из неё части.
        - preg_split: функция, задача которой разрезать строку по шаблону.
        
        Почему везде не использовать preg_match или preg_split? - Потому что задачи у них разные, для директив нужна вся строка, поэтому match. Тексту с аккордами же, нужно разделить на части. 

    * Нормализация - это процесс, при котором входные данные приводятся к одному (как правило нижнему) регистру, исключаются лишние пробелы и т.д. Так например "Яблоко" "ЯБЛОКО" "яблоко" после нормализации будут приведены к единому виду "яблоко" "яблоко" "яблоко", что в дальнейшем у нас в проекте используется для вычисления ХЭШа и дедубликации.

    * Front controller patern - Позволяет делать более структурированную архитектуру, раньше каждый URL вел к отдельному файлу, было не очень, тяжело поддерживать. Но сейчас, все URL ведут к одному index.php, который по сути играет роль хаба. Далее роутер определяет что за URL, и отправляет к контроллеру.

    * Symfony Routing standalone - Библиотека, позволяющая сопоставлять URL с контроллерами, позволяет создавать коллекцию маршрутов а после при помощи urlMatcher определяет по URL маршрут.
        - Пример в коде: 
        $routes = new RouteCollection(); - создает коллекцию маршрутов
        $routes->add('songs_list', new Route('/', ['_controller' => 'SongController', '_method' => 'list'])); - опрделяет, что при встрече '/' (http://localhost:8000/), будет обрабатываеться контроллер 'SongController' с методом 'list'.

    * Twig - шаблонизатор, позволяет отделить php от html. Twig не дает писать логику php в html, мы не можем обратиться к базе из шаблона, только {% if %}, {% for %} {{ var }}. Полезная фича - автоматическое экранирование, все переменный, которые попадают в {{ var }}, автоматом проходят через htmlspecialchars(). Так же, twig поддерживает наследование, что позволяет создать основной файл-каркас с хедером, футтером и т.д., для наледования дочерними элементами, можно переопределить что нужно. Используетя во многих коммерческих проектах.
        - Синтаксис  
            {{ song.title }} - Вывести значение (автоматически экранируется)
            {% if songs %}...{% endif %} - Команда (условие, цикл, блок)
            {# комментарий #} - Не попадёт в HTML

    * Request Context - выжимка из запроса, для роутера, хранит path, GET/POST.

    * PRG (Post-Redirect-Get) - В своем названии уже полностью иллюстрирует суть этого паттерна. Мы отправляем POST запрос на сервер, после чего выполняем редирект (Переход на другую страницу с изменением URL), и уже выполняем GET запрос на сервер, а тот в свою очередь в БД. Для чего это нужно? без редиректа, при создании песни, мы переходили бы на страницу с новой песней, но URL оставался таким же и при обновлении страницы отправлялся такой же POST запрос, как следствие создание дубликата.

    * Транзакции - служат для сохранения целостности данных при добавлении или изменении их в БД. Так например, у меня есть 100р и мне нужно перевести на другую карту, т.е. должно пройти 2 оперции: Снять 100р с моей карты; Положить 100р на другую карту. Но представим что во время обработки этих процессов, между ними произошел сбой, получается что 100р с карты сняли, но положить не положили. Транзакции позволяют исключить подобные ситуации путем двух функций rollback(), которая откатывает все операции при сбое, и commit() которая обрабатывается при успешной транзакции и вносит изменения. У нас в проекте транзакции используются при создании и обновлении песни, когда функции добавления песни в таблицу songs и добавление артистов в песню (таблица song_artists) обрабатываются отдельно друг от друга, что исключает добавление песни без артистов.

    * whitelist-валидация - проверяет пользовательский ввод по белому списку, если ввод не совпадает, игнор

    * Подход GET для фильтров, POST для изменений - GET позволяет копировать URL с данными либо кэшировать.

    * Сохранение состояния фильтров при помощи selected, позволяет не терять данные в поле ввода при обновлениии фильтров. Без него, выбрал фильтр, страница обновилась, выбранный фильтр в поле пропал, неудобно.

    * REST-подход: один URL может иметь разные HTTP-методы и как следствие разные действия.

    * Repository pattern: Отделение доступа к данным от бизнес логики. Контроллер орудует инструментами, а сами инструменты собирает репозиторий. Контроллеры теперь не обращаются к БД, не делают запросы. Сейчас они обращаются к репозиториям, передавая им необходимую инфу, а те в свою очередь уже обращаются к БД.


5. Forward-compat поля и зачем они:
    * Forward-compat поля нужны для будущего, в данный момент мы находимся на этапе планировки нашего "Дома", зачем в дальшнем ломать и строить новые стены? можно же заранее все спланироавть, пусть и не использовать. В дальнейшем это потребует намного больше времени и ресурсов.
        - Source: хранит в себе информацию откуда эта песня, в данный момент имеет значени "self", т.к. мы сами добавляем песни в базу, в дальнейшем песни будут добавляться разными способами: 
            1) "imported" - импортирование из других источников; 
            2) "ugc" - расшифровывается как User-Generated Content, пользователь добавил песню через форму, требует подтверждения на отсутсвие каких-либо ошибок;
            3) "self" - Мы как админ либо лидер группы прославления можем добавлять свои песни, подтверждение не нужно т.к. мы ведь сами можем проверить свои песни.
        
        - License: хранит в себе информацию о принадлежности песни. Сейчас по-умолчанию "unknow", но в дальнейшем юр. вопрос.(Я конечно верю что в нашем обществе вопрос о судебных исках и не стоит, но это ведь будет настоящий публичный продукт в дальнейшем, такая вещь обязана присутствовать)
            1) "public_domain" - Старые "народные" песни, из песенника например. В подтверждении авторами не нуждается.
            2) "ugc" - User-Generated Content, с согласия автора песни
            3) "unknow" - просто не указано, теоритически рискованно, но вероятно до Bethel или Брэндона Лэйка наше приложение не дойдет, если бы я был пользователем который хочет добавить их песню, я бы указал именно unknow, врятле они будут иметь какие-то претензии
            4) "restricted" - Защищено копирайтерами. Можно использовать песню чисто для себя в своем личном кабинете, но не для общего пользования. Либо, например песня находится в состоянии "restricted" пока ждут ответа от автора, если тот не против, то лицензия уже меняется на public_domain например.
        
        - Fingerprint: служит для исключения дубликатов. На данный момент вичисляется при сохранении (SHA-256 от названия + первой строки + первого артиста), но использоваться не будет. Сейчас он не нужен, но в дальнейшем разные пользователи могут добавлять одну и ту же песню с маленькими отличиями в названии (например), система считает fingerprint новой песни потом ищет в базе, если находит совпадение говорит: "Эта песня уже есть".

        - Role: это поле говорит о том, какую роль артист оказывал в этой песне, исполнитель, композитор, переводчик и т.д. Сейчас performer, я думаю нету смысла писать про каждую роль, и так поняно. 7. Заметки
    * REGEX в контексте проекта (на момент записи, моё объяснение может показаться не структурированным, планирую немного переформулировать в будущем):
        - Мы пропускаем наши данные, через парсер, в нашем случае: title, который используется для отображения названия песни, key для отображения тональности и текст. Что происходит: он встречает строку, в которую мы записали входные данные в chordPro формате, после чего, мы разбиваем нашу строку на другие отдельные строки, при помощи функции explode(), где в качестве параметров мы указываем '\n' (то есть при встрече) и нашу переменную в которой хранится наша строка в формате chordPro, эта функция разбивает строку на строки, которые хранятся у нас в переменной $lines, после чего мы проходимся по каждой строке внутри $lines при помощи foreach, удаляем лишние пробелы в начале и конце строки при помощи функции trim(), после чего записываем в новую переменную $trimmed, и проверяем, если, после функции trim() остается пустая строка, то это осознанный пробел, для разделения текста и мы оставляем ей пустое значение, и указываем в типе blank, то есть пустая строка, и идем дальше по циклу при помощи команды continue. Далее, если после всех махинаций мы получили не пустую строку, значит идет еще одна проверка, функция preg_match принимает в качестве параметров: схему (что должен увидеть, и если всё совпадает и ты увидишь "+" записываешь в 3 параметр (у нас в коде массив $matches)), второй параметр это наша передаваемая строка (уже обработанная функцией trim() и проверенная на пустоту своей сущности), третий параметр это массив $matches, который является массивом и хранит в себе: [0]->оригинал нашей строки; [1]-> 1-ый плюсик (то есть title/key/c (comment)) [2]-> 2-ой плюсик (значение) . Когда функция preg_match выявила совпадения и записала результаты "плюсиков" в наш массив идет проверка директивы, если $directive === "title" либо "key" это наши meta-данные записываем директиву и ее значение в массив $result['metadata'], а если $directive === "c", comment (например Verse 1), в таком случае мы в $result['section'] записываем type='comment' а в 'text'="Verse 1".

        - Дальше, мы разбираем текст с аккордами: И так, у нас есть переменная $parts которая хранит результат работы функции preg_split(), который разрезает нашу строку на части, по указанному "рисунку" - первому параметру, второй параметр - "$trimmed" это наш текст, который не попал в прошлый цикл из-за отсутствия фигурных скобок. третий параметр - "-1" показывает что функция может не ограничиваться в том, на сколько частей ему нужно порезать нашу строку, четвертый параметр - "PREG_SPLIT_DELIM_CAPTURE" используется для того, чтобы наши аккорды функция не выбрасывала, оставляя только текст, а наоборот оставила их (По логике функции, раз мы просим порезать по [] значит они и все что в них тебе не нужно и выбрасывает). Дальше идет переменная $lineparts = [], которая хранит в себе результат нашего цикла foreach. Что происходит в цикле: разбиваем наши $parts на $part, если натыкаемся на пустую строку - следующая итерация, далее, если мы натыкаемся на квадратные скобки (по шаблону), значит мы наткнулись на аккорд, берем наши квадратные скобки и то что в них и записываем в переменную $currentChord, следующая итерация натыкается не на фигурные скобки, а на простой текст, значит наш $currentChord принадлежит этому тексту, записываем в $lineParts[] = ['chord' => $currentChord, 'text' => $part], сбрасываем $currentChord и идем дальше. В конце цикла в конец цикла $result['sections'] добавляется новая запись с 'type' => 'line' и 'parts' => $lineParts.
